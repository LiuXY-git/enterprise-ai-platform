# Day 81：复杂销售业务任务测试

原路线要求测试复杂业务任务，以销售分析为例。本日将现有销售查询、错误恢复、任务日志和人工确认纳入一套固定场景验收，检查组合后的行为是否符合业务预期。

## 做了什么

新增 15 个场景，覆盖月度/客户销售额、无数据、范围澄清、工具重试和次数耗尽、模型回答降级、错误参数或金额、人工拒绝、内容修订、审批过期、重复与并发批准，以及两个销售任务的审批隔离。

每个场景从 Day 80 CLI 入口开始，真实启动 MCP 子进程并查询虚构销售库。后续审批动作由测试驱动程序在隔离目录中自动模拟，通过独立进程验证已保存的内容。模型仍为 fixture，不发起真实 Qwen 请求。

校验既检查输出金额、范围和引用，也检查 SQLite 实际保存的审批状态、批准事件和模拟发送记录。金额等期望值写在场景清单中，不通过被测代码重新计算一份答案来自我验证。

## 有什么用

单个组件能运行，不代表串联后仍正确。例如工具查询正确但审批绑定了另一项任务、重试成功却绕过人工确认、重复批准产生两次记录，都必须在整体流程中检查。

这套场景形成后续改动的对照基准。Day 82 调整 Prompt 或后续修改流程时，可以复跑它，检查原有业务与审批边界是否被破坏。当前使用固定模型样例验证程序行为，不能把离线通过率解释为真实模型准确率。

## 如何学习

按 [操作教程](../experiments/day81/README.md)先执行 `customer_approve`，确认 C001 的 2 单、1550.00 元与全客户的 4 单、3000.00 元不同；再运行全部场景，查看汇总报告和单场景 `trace.json`。

特别关注 `tool_exhausted` 和 `invalid_report`：验收结果应该是 `passed`，但业务结果分别是 `failed`、`rejected`，模拟执行数都是 0。这表示拦截符合预期，不能算作业务成功。

再观察 `cross_task_approval`：同一目录内创建两个不同范围的任务，全客户任务的摘要不能用于批准 C001 任务；客户任务执行后，全客户任务仍应保持等待。

## 交付与验证

交付场景清单、可重复执行的验收 CLI、反向校验测试、业务追踪记录及学习文档。证据入口为 [validation.json](evidence/day81/validation.json)，15 个场景汇总见 [report.json](evidence/day81/acceptance/report.json)。

相关既有测试与 Day 81 新增测试分别运行，统计不重复；还检查 Ruff、文档链接及已发布 v0.5 冻结资产。所有业务数据均为虚构，审批决定由测试程序模拟，真实模型请求和真实消息发送均为 0。

本次共 518 项测试通过：39 项新增测试、479 项既有回归，无失败、错误或跳过。15 个业务场景在新增测试中完整运行一次，保存了 16 次真实 MCP 工具调用的流程证据；这些场景已经计入新增测试，不另行重复计数。

本日没有修改生产 Prompt、Days 78–80 业务实现或历史版本清单；没有重跑全部 API/Docker 与历史发布测试，也未实现任意目标规划、季度趋势分析或真实企业权限体系。
