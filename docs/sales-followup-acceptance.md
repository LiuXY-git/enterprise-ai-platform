## 3 Day 46 设计验收

### 3.1 业务边界

检查项：

- 销售是销售建议的最终确认者。
- AI 只总结、提取缺失信息并提出内部建议。
- 程序负责输入校验、优先级、复核分支、数据保存和通知。
- 系统不自动联系客户。
- 系统不自动报价、承诺折扣、产品能力或交付时间。
- 客户输入不能决定通知接收者或改变系统权限。

通过标准：以上边界全部在设计文档中明确说明。

### 3.2 正常流程

检查顺序：

1. 校验并规范化客户输入。
2. 登记工作流运行。
3. 根据 `should_process` 拦截重复事件。
4. 调用 AI 生成结构化分析。
5. 校验 AI 输出并执行确定性业务规则。
6. 保存客户和跟进记录。
7. 生成通知预览或调用通知接口。
8. 分别保存工作流状态和通知状态。

通过标准：CRM 保存成功之前不得调用通知接口。

### 3.3 输入契约

必须定义以下字段：

- `event_id`
- `customer_id`
- `company_name`
- `industry`
- `requirement`
- `purchase_window_days`
- `budget_range`
- `sales_owner`
- `report_date`

通过标准：

- 每个字段都有类型、必填性、长度或取值范围。
- 未定义字段被拒绝。
- 空白需求被拒绝。
- 无效日期被拒绝。
- 调用方不能提交通知接收者和系统凭据。

### 3.4 标识符与去重

检查以下职责是否分开：

| 标识符 | 职责 |
| --- | --- |
| `customer_id` | 稳定标识客户 |
| `event_id` | 标识一次业务事件 |
| `run_id` | 标识一次平台运行 |
| `n8n_execution_id` | 标识一次 n8n 执行 |

通过标准：

- 工作流使用 `(workflow_name, event_id)` 识别重复事件。
- 相同事件不会再次调用 AI、写入跟进记录或发送通知。
- 重复请求不会覆盖首次保存的输入。
- 新的客户需求使用新的 `event_id`。

### 3.5 AI 输出契约

AI 输出必须包含：

- `summary`
- `needs`
- `missing_information`
- `next_actions`
- `risk_flags`

通过标准：

- JSON Schema 禁止额外字段。
- 所有字段都有类型和数量限制。
- 风险标识只能使用允许值。
- 未知信息进入 `missing_information`。
- AI 不直接决定最终优先级。
- AI 不决定通知接收者。

### 3.6 优先级

确定性规则：

| 采购评估窗口 | 优先级 |
| --- | --- |
| 小于或等于 30 天 | `high` |
| 大于 30 天 | `normal` |
| 未提供 | `normal`，并提示补充采购时间 |

通过标准：相同输入必须得到相同优先级，不依赖模型自由判断。

### 3.7 人工复核

以下情况必须进入人工复核：

- AI 输出不符合结构契约。
- 涉及未经确认的产品能力。
- 涉及价格或折扣。
- 涉及交付承诺。
- 包含 Prompt 注入风险。
- 可能包含不适合普通通知的敏感信息。

普通信息缺失不自动进入人工复核。

通过标准：`failed` 和 `needs_human_review` 的语义没有混用。

### 3.8 CRM 数据设计

必须设计：

- `customers` 表。
- `followup_records` 表。
- 客户与跟进记录的一对多关系。
- `followup_records.run_id` 唯一约束。
- SQLite 外键约束。
- CRM 事务写入顺序。

通过标准：同一工作流运行最多创建一条跟进记录。

### 3.9 通知设计

通知状态必须包含：

- `pending`
- `preview`
- `sent`
- `failed`
- `delivery_unknown`
- `skipped`

通过标准：

- 工作流状态和通知状态分别记录。
- 预览模式不调用真实消息接口。
- `sent` 不解释为接收者已读。
- `delivery_unknown` 禁止自动重发。
- 通知失败不会删除已经保存的 CRM 记录。

## 4 验收样例文件检查

`demo/sales-followup-cases.json` 应满足：

- 是合法 JSON。
- 根对象包含 `workflow_name`、默认通知配置和 `cases`。
- 包含 A01 至 A15 共 15 个场景。
- 15 个场景 ID 全部唯一。
- 不包含真实客户数据、密钥、Token 或真实接收者。

场景覆盖关系：

| 编号 | 场景 | 主要断言 |
| --- | --- | --- |
| A01 | 正常高优先级线索 | 保存 CRM，生成通知预览 |
| A02 | 预算未知 | 不编造预算，不强制复核 |
| A03 | 采购窗口大于 30 天 | 优先级为 normal |
| A04 | 采购窗口未知 | 提示补充采购时间 |
| A05 | 需求为空 | 输入阶段拒绝 |
| A06 | 请求指定通知接收者 | 拒绝额外字段 |
| A07 | 重复业务事件 | 不重复分析、写入或通知 |
| A08 | Prompt 注入 | 转人工复核 |
| A09 | 报价和折扣要求 | 转人工复核，不作承诺 |
| A10 | AI 输出结构非法 | 不保存正常跟进记录，不通知 |
| A11 | AI 服务不可用 | 记录 failed |
| A12 | CRM 事务失败 | 回滚并停止通知 |
| A13 | 通知明确失败 | 保留 CRM，记录 failed |
| A14 | 通知结果不确定 | 禁止自动重发 |
| A15 | 预览模式 | 不调用真实通知接口 |

## 5 Day 47 实现验收

本节已在 2026-09-10 完成代码和本地运行验收。

### 5.1 数据库验收

检查：

- 应用初始化后两张 CRM 表存在。
- 客户 ID 具有唯一约束。
- 跟进 ID 和运行 ID 具有唯一约束。
- SQLite 外键检查已启用。
- 同一客户可以保存多条不同事件的跟进记录。
- 同一 `run_id` 不能创建两条跟进记录。
- CRM 事务失败时不会留下半条数据。

### 5.2 API 契约验收

检查 OpenAPI 是否包含计划中的 CRM 接口，并确认：

- 请求模型禁止额外字段。
- 字符串会去除首尾空白。
- 非法标识符返回 422。
- 空白需求返回 422。
- 非法日期返回 422。
- 响应不会暴露内部数据库编号或凭据。
- 销售助手只调用一次 `POST /crm/followups` 完成关键 CRM 写入。
- 客户新增或更新与跟进记录创建位于同一个数据库事务中。
- 工作流不会先调用客户接口，再通过第二个请求创建跟进记录。

### 5.3 工作流验收

按顺序执行：

1. A01 正常场景。
2. A02 预算未知场景。
3. A03 和 A04 优先级场景。
4. A07 重复事件场景。
5. A08 和 A09 人工复核场景。
6. A15 通知预览场景。

验收证据应包括：

- n8n 执行成功记录。
- FastAPI 响应。
- 工作流运行记录。
- 客户记录。
- 跟进记录。
- 通知预览正文。

预览验收不需要真实消息送达截图。

### 5.4 自动化测试

Day 47 至少覆盖：

- 输入模型校验。
- 优先级计算。
- 客户新增和更新。
- 跟进记录创建。
- `run_id` 去重。
- 客户跟进记录查询。
- 正常通知预览。
- 重复事件不产生副作用。
- OpenAPI 契约。

## 6 Day 48 故障验收

本节在 Day 48 完成错误处理后执行。

### 6.1 AI 故障

使用 A10 和 A11 验证：

- 非法结构进入人工复核。
- 服务不可用记录为 failed。
- 两种状态不会混淆。
- 异常消息不包含模型密钥或上游敏感响应。

### 6.2 CRM 故障

使用 A12 验证：

- 客户和跟进记录处于同一事务。
- 写入失败时事务回滚。
- CRM 失败后不调用通知接口。
- 失败记录包含阶段和安全错误类别。

### 6.3 通知故障

使用 A13 和 A14 验证：

- 通知失败后保留客户与跟进记录。
- 明确失败和结果不确定分别记录。
- 使用稳定通知请求标识。
- `delivery_unknown` 不自动重发。
- 人工可以根据 `run_id` 查询业务结果和通知状态。

### 6.4 分阶段恢复

验证恢复逻辑不会重复完成已经成功的阶段：

| 已完成阶段 | 恢复起点 |
| --- | --- |
| 仅登记工作流 | AI 分析 |
| AI 分析完成，CRM 未保存 | CRM 保存 |
| CRM 已保存，通知未请求 | 通知处理 |
| 通知明确失败 | 等待人工决定 |
| 通知结果不确定 | 人工核对实际送达情况 |
