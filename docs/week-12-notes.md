## Day 78：让 Agent 执行过程可追踪


路线要求：记录“用户请求 → Agent 决策 → 调用工具 → 结果 → 最终回答”。本日用代码将这条链保存下来，便于学习、定位失败和后续设计恢复机制。

<a id="day78-今天完成什么"></a>

### 今天完成什么

为已有 Day 73 MCP 销售查询新增日志包装层，使用 SQLite 保存每次任务及其事件。可在任务运行后关闭终端，再通过任务编号查看同一条记录。默认不调用真实模型，但 MCP 服务子进程与虚构数据库查询真实运行。

任务开始先保存固定用户请求；模型返回后记录“提出工具调用”或“提出回答”；参数通过现有校验后记录工具调用，得到合格回执后记录金额与范围相关摘要；将回执引用与下一轮模型输入关联；最终通过核对后记录本地模板回答。最终事件与任务状态一次事务提交。

“Agent 决策”是可观察的动作摘要，不是记录模型内部推理。模型提出调用并不意味着工具已执行；`tool_call` 表示应用已接受参数、准备尝试，`tool_result` 才表示拿到了通过校验的结果。

<a id="day78-有什么用"></a>

### 有什么用

例如最终销售额错误，可以沿日志检查：请求是不是 9 月、参数是否通过、工具合计是不是 3000.00 元、模型回答是否与回执一致。若最后停在调用工具，则需要调查服务是否返回，不能直接判定没有执行。

| 概念 | 回答的问题 | 当前实现 |
| --- | --- | --- |
| Day 75 会话记忆 | 下次对话可以使用哪些上下文？ | 按会话保存固定部门偏好 |
| Day 60 检查点 | 模拟任务已经执行到哪一步？ | 保存状态并恢复模拟进度 |
| Day 78 任务日志 | 这次运行发生过哪些事件？ | 保存事件并按序查看 |
| Day 79 错误恢复 | 失败后允许采取什么行动？ | 后续实施 |

<a id="day78-学习顺序"></a>

### 学习顺序

1. 按 [可复刻操作流程](../experiments/day78/README.md)运行 `monthly`，取得任务编号。
2. 用 `show` 查看 11 条事件，找到请求、工具参数、3000.00 元结果与最终回答。
3. 在新终端运行 `list` / `show`，确认旧记录仍在。
4. 运行 `clarification`，对比没有工具调用的 6 条事件。
5. 阅读 `test_failure_before_tool_prevents_execution` 与 `test_terminal_event_and_status_are_atomic`，理解日志失败为什么也需要停止执行。

自测：`agent_decision` 是否证明工具已经执行？`running_or_interrupted` 是否代表可以直接重试？查看日志是否会再次扣模型额度？答案分别是：否；否，需要结合执行结果与后续恢复策略；否，查看为只读操作。

## Day 79：Agent 错误恢复


路线目标：工具失败后可以重新尝试，或更换方案。本日将恢复策略写入独立 CLI，并沿用 Day 78 的任务日志，便于解释每次恢复为何发生、执行几次、最终如何结束。

<a id="day79-今天的实现"></a>

### 今天的实现

固定只读 MCP 工具遇到超时或传输错误后最多重试一次，重新建立连接、发现和校验工具，保持原参数及虚构数据库快照。模型超时、网络错误和 HTTP 502/503/504 也可在每个逻辑轮次内重试一次。

如果工具已返回有效回执，但最后的模型回答连续失败，则更换回答方案：从本次回执构造本地模板答案，明确标记 `degraded=true` 和 `answer_source=validated_receipt_fallback`。模型给错金额、工具结果异常或参数越界时不会走此路径。

若工具两次都没有拿到有效结果，就停止并记录失败，不编造结果、不查询旧任务缓存、不绕过 MCP 直接访问 SQL。日志写入失败同样会停止后续恢复操作。

<a id="day79-具体作用"></a>

### 具体作用

以前一次偶发超时会让整个任务失败，现在允许有限重试；模型暂时无法组织回答，但可信工具结果已经取得时，仍可交付标明来源的固定格式结果。错误无法恢复时，用户能从日志看到失败和停止原因。

可恢复不等于所有操作都能重复：本实验仅查询程序创建的临时虚构销售库，没有写入副作用。超时后仍可能已经执行过读取，日志保持未知结果语义。发送消息、付款或修改客户数据需要另行设计幂等及授权机制，不能直接套用本实验的重试策略。

<a id="day79-学习与复刻"></a>

### 学习与复刻

详细命令见 [Day 79 实验流程](../experiments/day79/README.md)。建议依次运行：

1. `tool_timeout_once`：查看一次逻辑工具调用对应两次尝试。
2. `tool_timeout_always`：确认只尝试两次，然后失败停止。
3. `report_timeout`：确认有效回执被用于模板回答，且明确标记降级。
4. `invalid_report`：金额错误时拒绝，不通过重试或降级隐藏错误。
5. `invalid_arguments`：越界参数在执行工具前被拦截。

每次运行后用 `show` 查看 `phase=recovery` 的 `retry`、`stop` 或 `fallback` 事件。`stop` 表示当前操作不再重试；最终模型停止重试后，如果满足条件，任务仍可能转入模板降级。最终任务状态以 `final_answer` 为准。

## Day 80：Human in the Loop 人工确认


目标是让 Agent 在执行需要确认的操作前暂停，由使用者查看具体内容并决定是否继续。本日采用“销售简报发送前确认”教学场景，执行结果是本地模拟发送记录。

流程为：查询虚构销售数据 → 校验简报 → 创建待审批单 → 展示内容 → 人工批准或拒绝 → 批准后写入一条本地模拟记录。不会真实发送消息。

<a id="day80-今天完成的能力"></a>

### 今天完成的能力

生成阶段复用 Day 79 的 MCP 查询与错误恢复，生成日志继续使用 Day 78 格式；审批阶段使用独立 SQLite 表保存具体内容、版本、有效期、决定及模拟结果，通过 `source_task_id` 关联两部分记录。

待审批记录持久化后，即可退出程序，在新进程中继续查看和决定。CLI 提供 `create`、`list`、`show`、`approve`、`reject`、`revise` 和 `task-log`。生成阶段不自动调用批准，模型的工具列表中也没有批准工具。

批准必须提交审批编号、所查看内容的摘要，并显式输入 `--confirm APPROVE`。接收对象、正文、备注和来源都包含在摘要中。修改接收对象或备注后，会生成新审批版本并使旧版本失效；正文仍来自已有校验链，不允许直接改金额。

“批准事件、模拟发送记录、最终状态”在同一事务中提交。同一个审批编号重复或并发批准只产生一条模拟记录；任一必要写入失败会回滚整个事务。过期、拒绝、内容不匹配和被替代的审批都不能执行。

<a id="day80-有什么用"></a>

### 有什么用

Day 79 让程序能在特定故障后继续工作，Day 80 则让程序知道在哪里必须等待人的决定。即使查询自动重试成功或回答改用回执模板，也只是生成新的待审批事项，不会自动获得执行权限。

这一机制适合学习对外发送、修改业务记录等操作前的确认流程。本次只验证本地模拟动作；真实企业操作仍需要身份认证、权限分工和外部服务幂等设计。

<a id="day80-如何学习"></a>

### 如何学习

从 [详细复刻教程](../experiments/day80/README.md)开始，按以下顺序练习：

1. 创建审批单，看见 `pending` 和 `simulation_count=0`。
2. 查看正文、接收对象和内容摘要，再批准；观察状态变为 `executed`，模拟记录数为 1。
3. 重复批准相同编号，确认没有第二条模拟记录。
4. 新建一份并拒绝，确认不能随后批准。
5. 修改待审批备注，用旧编号或旧摘要尝试批准，观察拦截。
6. 创建短有效期审批，过期后观察 `effective_status` 与阻止执行。
7. 查看 `task-log`，理解错误恢复与人工确认之间的关系。

思考：程序重启后还能审批，是否表示原 Agent 计算可以从中断处恢复？不是；保存的是完整的待审批事项。内容摘要是否证明操作者是某位员工？不是；它只绑定内容版本。

<a id="day80-验收与边界"></a>

### 验收与边界

验证记录见 [validation.json](evidence/week-12.md#day80)、CLI 演示和 JUnit 文件。测试包括未批准零执行、拒绝、过期、内容修订、重复与跨进程并发批准、事务故障及进程中断恢复，以及查询失败不创建审批单。

本日不新增真实模型请求，不实现真实消息发送、多用户审批权限、完整 Agent 重启续跑或平台 API/Docker 集成。旧版 v0.5、Day 78 和 Day 79 代码保持不变；仅回归相关测试并检查冻结资产，不声称重跑所有历史发布或平台测试。

## Day 81：复杂销售业务任务测试


原路线要求测试复杂业务任务，以销售分析为例。本日将现有销售查询、错误恢复、任务日志和人工确认纳入一套固定场景验收，检查组合后的行为是否符合业务预期。

<a id="day81-做了什么"></a>

### 做了什么

新增 15 个场景，覆盖月度/客户销售额、无数据、范围澄清、工具重试和次数耗尽、模型回答降级、错误参数或金额、人工拒绝、内容修订、审批过期、重复与并发批准，以及两个销售任务的审批隔离。

每个场景从 Day 80 CLI 入口开始，真实启动 MCP 子进程并查询虚构销售库。后续审批动作由测试驱动程序在隔离目录中自动模拟，通过独立进程验证已保存的内容。模型仍为 fixture，不发起真实 Qwen 请求。

校验既检查输出金额、范围和引用，也检查 SQLite 实际保存的审批状态、批准事件和模拟发送记录。金额等期望值写在场景清单中，不通过被测代码重新计算一份答案来自我验证。

<a id="day81-有什么用"></a>

### 有什么用

单个组件能运行，不代表串联后仍正确。例如工具查询正确但审批绑定了另一项任务、重试成功却绕过人工确认、重复批准产生两次记录，都必须在整体流程中检查。

这套场景形成后续改动的对照基准。Day 82 调整 Prompt 或后续修改流程时，可以复跑它，检查原有业务与审批边界是否被破坏。当前使用固定模型样例验证程序行为，不能把离线通过率解释为真实模型准确率。

<a id="day81-如何学习"></a>

### 如何学习

按 [操作教程](../experiments/day81/README.md)先执行 `customer_approve`，确认 C001 的 2 单、1550.00 元与全客户的 4 单、3000.00 元不同；再运行全部场景，查看汇总报告和单场景 `trace.json`。

特别关注 `tool_exhausted` 和 `invalid_report`：验收结果应该是 `passed`，但业务结果分别是 `failed`、`rejected`，模拟执行数都是 0。这表示拦截符合预期，不能算作业务成功。

再观察 `cross_task_approval`：同一目录内创建两个不同范围的任务，全客户任务的摘要不能用于批准 C001 任务；客户任务执行后，全客户任务仍应保持等待。

<a id="day81-交付与验证"></a>

### 交付与验证

交付场景清单、可重复执行的验收 CLI、反向校验测试、业务追踪记录及学习文档。证据入口为 [validation.json](evidence/week-12.md#day81)，15 个场景汇总见 [report.json](evidence/week-12.md#day81)。

相关既有测试与 Day 81 新增测试分别运行，统计不重复；还检查 Ruff、文档链接及已发布 v0.5 冻结资产。所有业务数据均为虚构，审批决定由测试程序模拟，真实模型请求和真实消息发送均为 0。

本次共 518 项测试通过：39 项新增测试、479 项既有回归，无失败、错误或跳过。15 个业务场景在新增测试中完整运行一次，保存了 16 次真实 MCP 工具调用的流程证据；这些场景已经计入新增测试，不另行重复计数。

本日没有修改生产 Prompt、Days 78–80 业务实现或历史版本清单；没有重跑全部 API/Docker 与历史发布测试，也未实现任意目标规划、季度趋势分析或真实企业权限体系。

## Day 82：优化 Agent Prompt


按 Week 12 路线，在固定销售查询中减少模型猜测、范围偏移和错误字段映射的机会，并建立可以复跑的对照入口。本日交付候选 Prompt 与评估工具，没有宣称已经测得模型幻觉率降低。

<a id="day82-实现"></a>

### 实现

- 独立的 [候选 Prompt](../experiments/day82/candidate.md)：划分调用工具前后两个阶段，按回执逐字段填写报告，强调全量金额、明细截断、无数据、来源引用和审批边界。
- [注入适配器](../experiments/day82/prompt_policy.py)：保留宿主校验与模型输出，只在转交模型时替换 system 内容；记录版本摘要和实际输入。
- [对照与集成入口](../experiments/day82/prompt_lab.py)：基线/候选使用相同场景，交替运行顺序，每例独立会话；可选真实模型对照有总请求上限，无自动重试。
- 新版 `prepare` 复用日志、错误恢复与待审批流程；没有自动批准，也没有对外发送。
- [16 个固定样例](../experiments/day82/cases.json)和[可复刻教程](../experiments/day82/README.md)。

<a id="day82-本次验证"></a>
