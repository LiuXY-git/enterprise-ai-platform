# Day 78：让 Agent 执行过程可追踪

路线要求：记录“用户请求 → Agent 决策 → 调用工具 → 结果 → 最终回答”。本日用代码将这条链保存下来，便于学习、定位失败和后续设计恢复机制。

## 今天完成什么

为已有 Day 73 MCP 销售查询新增日志包装层，使用 SQLite 保存每次任务及其事件。可在任务运行后关闭终端，再通过任务编号查看同一条记录。默认不调用真实模型，但 MCP 服务子进程与虚构数据库查询真实运行。

任务开始先保存固定用户请求；模型返回后记录“提出工具调用”或“提出回答”；参数通过现有校验后记录工具调用，得到合格回执后记录金额与范围相关摘要；将回执引用与下一轮模型输入关联；最终通过核对后记录本地模板回答。最终事件与任务状态一次事务提交。

“Agent 决策”是可观察的动作摘要，不是记录模型内部推理。模型提出调用并不意味着工具已执行；`tool_call` 表示应用已接受参数、准备尝试，`tool_result` 才表示拿到了通过校验的结果。

## 有什么用

例如最终销售额错误，可以沿日志检查：请求是不是 9 月、参数是否通过、工具合计是不是 3000.00 元、模型回答是否与回执一致。若最后停在调用工具，则需要调查服务是否返回，不能直接判定没有执行。

| 概念 | 回答的问题 | 当前实现 |
| --- | --- | --- |
| Day 75 会话记忆 | 下次对话可以使用哪些上下文？ | 按会话保存固定部门偏好 |
| Day 60 检查点 | 模拟任务已经执行到哪一步？ | 保存状态并恢复模拟进度 |
| Day 78 任务日志 | 这次运行发生过哪些事件？ | 保存事件并按序查看 |
| Day 79 错误恢复 | 失败后允许采取什么行动？ | 后续实施 |

## 学习顺序

1. 按 [可复刻操作流程](../experiments/day78/README.md)运行 `monthly`，取得任务编号。
2. 用 `show` 查看 11 条事件，找到请求、工具参数、3000.00 元结果与最终回答。
3. 在新终端运行 `list` / `show`，确认旧记录仍在。
4. 运行 `clarification`，对比没有工具调用的 6 条事件。
5. 阅读 `test_failure_before_tool_prevents_execution` 与 `test_terminal_event_and_status_are_atomic`，理解日志失败为什么也需要停止执行。

自测：`agent_decision` 是否证明工具已经执行？`running_or_interrupted` 是否代表可以直接重试？查看日志是否会再次扣模型额度？答案分别是：否；否，需要结合执行结果与后续恢复策略；否，查看为只读操作。
